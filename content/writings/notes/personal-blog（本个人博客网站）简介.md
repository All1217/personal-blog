# 1 如何管理静态文章资源

```
content/
└── writings/
    ├── anime/ # 专放动漫杂谈类文章，加载器扫描到该目录名称时会识别出这是动漫杂谈大类
    │   └── Puella-Magi-Madoka-Magica1/ # 加载器扫描到文件夹名称直接将其作为文章名称显示在网页上
    │       ├── zh.md
    │       ├── 封面.jpeg
    │       ├── 配图1-意气风发.png
    │       ├── 配图2.png
    │       ├── 配图3.png
    │       ├── 配图4.png
    │       ├── 配图5.png
    │       ├── 配图6.png
    │       ├── 配图7.png
    │       ├── 配图8.png
    │       ├── 配图9.png
    │       └── 配图10.png
    ├── career/ # 专放生涯规划类文章
    │   └── Analysis of Popular College Metrics (v1.0)/
    │       ├── zh.md
    │       └── Analysis_of_Popular_College_Metrics_cover.png
    └── notes/ # 专放技术笔记类文章
        └── personal-blog（本个人博客网站）简介.md
```

不接数据库，采用市场常见做法：将一篇文章和其配图放在同一个文件夹，目录树本身包含分类功能，项目构建后当成可引用的静态文件，Hugo、Astro、VitePress、Hexo 都是这条路。

为了实现多语言切换，中文和英文文章一式两份放在同一个文件夹里。中文命名为`zh.md`，英文命名为`en.md`，网页检测到当前是中文模式，就加载`zh.md`，检测到是英文模式，就加载`en.md`

这种模式适合文章数量少（几百篇以内）、无评论点赞等复杂交互场景的文档网站。

# 2 模糊匹配

本博客的`文字创作`板块支持按关键词全文检索，这并没有动用后端的 Elasticsearch 之类的复杂实现，而是纯前端。库是 [Fuse.js](https://www.fusejs.io/)，实现见 `src/composables/useWritingSearch.ts`。

普通搜索（KMP算法、Boyer-Moore 和暴力搜索这类算法）只问一件事：这段文字里有没有连续出现这几个字。少打一个、多打一个、顺序反了，就找不到。比如我要在`打车去高新街的城市便捷酒店`这句话里查找关键词`高新街的城市便捷酒店`，关键词内部一个字不能少、不能多、不能变，否则就找不出来。如果原话变成：`高新街城市便捷酒店`、`高新路的城市便捷酒店`、`城市便捷酒店高新街店`，虽然表达的意思一样，但因为里面语序变了，或者某个字少了，它就找不出来了。所以这类算法不能直接应用在实际的模糊匹配应用场景中，得另寻他法。

Fuse.js 要解决的就是这个问题，它的思路是：要改几下，关键词才能和文章里的某一小段对上。改得越少就越相似，改得太多就不像。`高新街城市便捷酒店`相较于`高新街的城市便捷酒店`只少了一个“的”字，fuse.js认为它们之间改的很少，是“相似”的。它采用的算法和力扣上那道“编辑距离”算法题（ [编辑距离](https://leetcode.cn/problems/edit-distance/description/)）是同一个母题。

力扣第 72 题（ [编辑距离](https://leetcode.cn/problems/edit-distance/description/)）的题目是：给两个单词，只允许三种操作——插入一个字符、删除一个字符、替换一个字符——求把 `word1` 变成 `word2` 的最少操作次数。这个次数就叫编辑距离（Levenshtein distance）。两端文本之间的编辑距离越小，可以认为它们越相似。

力扣是算法练习网站，学的是抽象理论知识，它要的是两个完整字符串之间的一个整数（编辑距离），标准解法是填一张二维表：`dp[i][j]` 表示 `word1` 的前 `i` 个字符变成 `word2` 的前 `j` 个字符要几步。实际应用场景更复杂，要的可不仅仅是那一个数字。

相对于原版，Fuse首先需要考虑**「短关键词出现在长文的哪一段」，不是两整段互改。** 把关键词和整篇正文做力扣那道题，距离几乎等于正文长度减关键词长度，每篇文章都会「很远」，排序没有意义。Fuse 是在正文里滑动，找编辑距离足够小的那一小段。

**不算完整的最小距离，只问「差错次数够不够」。** 力扣必须给出精确的最少步数。搜索只需要知道像不像、谁更像。Fuse 用 Bitap：把关键词编成位掩码，从正文开头逐字扫。可以想成一排开关，读到对的字就往前拨一格；对不上也可以拨，但记一次差错，并同时保留「零差错走到哪」「一次差错走到哪」。差错用完还没走完关键词，这条路就废弃。它不填 `(正文长度 × 关键词长度)` 那张表，短关键词扫起来更快。三种差错和力扣一致：换一个字是替换，正文里多出来的字是插入，关键词里有、正文里没有的字是删除。

**距离被收成 0 到 1 的分数，再加门槛。** 0 是完全一样。`threshold: 0.36` 表示高于 0.36 的结果丢掉。设成 0 就退化成精确匹配。力扣没有这个截断，它总是返回答案。

**还要处理「出现在哪」和「哪一段文字更重要」。** 力扣的输入只有两个字符串。搜索还要决定：命中出现在标题还是出现在三千字正文的中间，谁该排前面。Fuse 默认会惩罚离这段文字开头太远的命中。正文很长，相关的句子往往在中间，所以本站打开了 `ignoreLocation: true`，位置不再扣分。多段文字再按权重合成一个总分，见 2.5。

**关键词最长按 32 个字符一段来算。** Bitap 靠 JavaScript 的位运算，而位运算只对 32 位整数有定义。更长的关键词会被切成几段分别匹配，再把结果合起来。力扣的二维表没有这个长度上限，只是表会更大。

## 2.3 为什么用编辑距离，而不是 KMP

KMP 解决的是另一道题：这段文字里有没有**原样**连续出现这个模式。它把已匹配的前缀记下来，失配时不要从头再比，从而做到线性时间。Boyer-Moore、`String.prototype.includes` 也是这个家族，差别只在怎么跳过不可能的位置。

它们都不能回答「差一个字还算不算」。搜「组建边界」时，正文里只有「组件边界」，KMP 的结论是不存在。编辑距离的题目定义里本来就包含插入、删除、替换，所以打错一个字仍然有距离、仍然能排序。模糊搜索要的就是这个定义，不是更快的精确查找。

倒排索引（Elasticsearch、Lunr 一类）是第三条路：先把文章切成词，再建「词 → 文章」的表，查的时候按词去取，而不是逐字扫全文。它适合语料很大、查询很频繁的场景。中文没有空格，切词本身就要一本词典或一个分词器；少打一个字时，切出来的词常常对不上，还得再在词上做一次编辑距离。本站文章不多，这条路的收益盖不住这套组件。

## 2.4 为什么本项目用 Fuse.js

文章在构建时已经打进前端包，打开页面时全部在内存里，数量停在几十到几百篇。搜索发生在浏览器里，没有单独的搜索服务。在这个前提下比过这些方案：

| 方案 | 不选的原因 |
|------|------------|
| `includes` 或自己写 KMP | 不能容忍错字，和「模糊」这个需求相反 |
| 自己按力扣填编辑距离表 | 比的是两整段文字，用在长正文上排序是错的；分数、门槛、多字段权重还得再写一遍 |
| Lunr、FlexSearch、MiniSearch | 倒排索引，语料变大后更合适，但中文切词要额外处理，对本站的文章量过重 |
| Elasticsearch | 要单独的服务和索引同步。本站没有后端，文章改完是重新构建，不是往搜索引擎推一条数据 |

Fuse.js 把 2.2 里那些改动都包好了：Bitap、0 到 1 的分数、`threshold`、多字段 `keys` 和权重、`ignoreLocation`。调用方只需要把当前栏目的文章摊成标题、摘要、栏目名、正文。代价是每次查询都线性扫过这些文章的正文，不能当成百万级文档的搜索引擎。文章数量明显上去之后，再换倒排索引。

## 2.5 本站实际怎么搜

搜索前先按栏目收窄，只在当前栏目的文章里找。每篇文章再摊成四段文字，各有权重：

| 字段 | 权重 | 原因 |
|------|------|------|
| 标题 | 2 | 标题撞上，比正文里偶然出现更该排前面 |
| 摘要 | 1.2 | 比正文重要，但不如标题 |
| 栏目名 | 1 | 搜「技术笔记」时能靠栏目命中 |
| 正文 | 0.5 | 参与全文检索，但不要压过标题 |

四段各自算出一个分数，再按权重合成一个总分，分数低的排前面。

输入框是空的时候不跑 Fuse，直接按日期列出当前栏目。切换中英文后，标题、摘要和正文换成当前语言，这份名单会重建，所以搜的是你正在看的那种语言，不是中英混在一起搜。
